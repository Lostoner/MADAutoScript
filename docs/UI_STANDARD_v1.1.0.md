# 跨项目 UI 设计规范

版本：1.1.0 · 制定日期：2026-11-11 · 更新日期：2026-11-13

让用户看懂当前状态、找到下一步，并可靠地完成任务。统一这些质量要求；配色、布局、技术栈和品牌表达由各项目决定。

配套的 `DESIGN.template.md` 是项目模板，采用时另存为 `DESIGN.md`。本规范适用于项目明确采用后的 UI 工作，不要求批量重构存量界面。

## 1. 从一个真实任务开始

1. **明确任务。** 写清主要用户、使用设备、最重要的 1–3 个任务，以及完成任务后用户能看到什么。
2. **确定项目规范。** 在获得该项目接入授权后，将模板另存为 `DESIGN.md`，填写核心决策，只保留适用的平台条款。把本规范一并保存，或链接到项目可访问的固定版本。
3. **先验证一条完整路径。** 选择真实操作页面，覆盖正常完成和最相关的失败恢复，再扩大应用范围。展示首页不能代替实际工作页面。

已有项目先记录当前组件、主题和必须保留的操作；没有明确收益，不更换技术栈、成熟组件或用户熟悉的入口。

## 2. 规则的范围与优先级

- **必须**：适用范围内的交付底线。影响关键任务的问题须修复，不能用视觉偏好抵消。
- **建议**：缺少既有规范时的默认选择。项目可根据内容、设备和用户需求调整，并写明替代规则。
- **按需**：只有存在对应功能或平台时才采用；没有的功能不为满足模板而新增。

决策顺序：用户明确目标和平台硬约束 → 本规范中适用的必须项 → 项目 `DESIGN.md` → 已选组件的具体实现 → 外部视觉参考。出现冲突时先查清依据；涉及改变用户目标或既有行为时取得相应决定，不静默覆盖。

本规范中的默认值不自动覆盖现有项目。项目规范须记录适用页面、新增规则及已接受的例外；既有问题与本次变更分开处理。选择某种视觉风格，不构成豁免可读性、操作反馈或安全要求的理由。

## 3. 信息层级服务于任务

### 必须

- 用户能识别当前位置、当前对象、可执行操作和操作结果。选中对象、当前筛选及批量操作范围必须明确。
- 每个独立任务区域有清晰的主操作，次要操作降低强调；危险操作与普通操作区分。不要把互不相关的任务强行合成一个主按钮。
- 内容分组反映真实关系。标题、间距和对齐优先于叠加边框；卡片用于独立内容单元，不给每一行套卡片。
- 重要内容不能仅因空间不足而消失。长标题、路径和表格内容被截断时，要能通过键盘、触控或展开查看完整值。
- 数字、单位、时间和状态来自真实数据。未知、未加载、无权限、零值不得互相代替；演示数据须明确标记。

### 建议

- 工具类界面把操作区、结果区和必要状态放在主要视野内，不先摆大型欢迎横幅、装饰图和无用统计卡。
- 阅读界面限制正文行宽；工作台让数据获得足够空间；展示页面和游戏允许更强的品牌与美术表达。
- 全局主题、工作空间等设置放在应用导航或顶栏；筛选、搜索放在作用区域附近。控件的位置应说明它影响全局、当前列表还是所选对象。
- 执行型工具的详情区优先呈现“对象 → 状态／进度 → 需要处理的问题 → 主操作与结果入口”，技术步骤和元数据随后按需展开。不要让用户先读完日志才能找到重试。
- 低频选项渐进展开，高频操作保持可见。错误摘要、影响范围和恢复动作不能藏进默认收起的详情；空状态给出适用的下一步，不重复解释整个产品。

## 4. 建立可维护的视觉系统

### 4.1 颜色与主题

- **必须**使用语义角色：背景、正文、辅助文字、控件边界、主要操作、焦点、选中和状态。名称描述用途，不把“蓝色”当作所有主要操作的含义。
- **必须**区分装饰分隔线与识别控件所必需的边界。低对比度分隔线不能成为输入框唯一的识别线索。
- **必须**区分品牌色和成功／警告／错误语义；状态同时用文字、图标或形状表达。图表也不能只靠红绿辨别系列。
- 支持哪些主题由项目决定。**必须**逐个检查已支持主题的文字、焦点、禁用、选中、弹层和图表，不用简单反色生成暗色主题。
- **建议**采用少量中性色和一个主要强调色；只有信息分类或产品表达需要时才扩展颜色体系。

**可选风格：暖白／石墨。** 没有既有主题的信息型工具，可采用暖白或石墨底色、低饱和绿强调、少量状态色；普通完成状态降低视觉强调，需要处理的异常保留清晰提示。配套模板提供这套色板和原有工具蓝色板，项目选用其一或沿用自身主题。字号层级、留白与交互规则不依赖这套配色，选色不要求新增深浅主题。

### 4.2 字体与中文排版

- **必须**为支持的语言规定字体回退链；支持中文时检查缺字、标点、中英文混排、数字和文件路径。正文保留可读取的文本信息，不固化成图片。
- **必须**给操作名称、输入、错误和状态说明留足字号与行高；空间不足时调整结构，不能持续缩小文字。
- **必须**让同一文字角色保持一致，并映射到已有文字样式或 token。标题级别表达内容结构，不仅用于套用字号。
- **建议**用字号、字重、间距共同区分层级；同一视图通常保留 3–4 个明显层级，避免每个字段都加粗、着色或使用不同字号。

没有既有规范的 Web 信息工具，建议从下表选取实际需要的角色。`rem` 随用户根字号变化，括号中的 CSS px 仅按默认 16px 根字号换算，不用于锁定根字号。

| 角色 | 建议字号 | 行高／强调方式 |
|---|---|---|
| 页面标题 | `2rem`（32px）；窄空间可到 `1.75rem`（28px） | 1.25–1.35；字重 500，必要时 600 |
| 区域／详情标题 | `1.25–1.375rem`（20–22px） | 1.35–1.45；字重 500 |
| 组内小标题 | `1.125rem`（18px） | 约 1.45；只在确有子分组时使用 |
| 正文、任务名称、主要输入 | `1rem`（16px） | 1.5–1.7；正文 400，选中名称可用 500 |
| 控件标签、辅助说明、元数据 | `0.875rem`（14px） | 约 1.5；通过位置和颜色区分，不继续缩小关键状态或错误 |
| 关键进度／结果数字（按需） | `2.5–3.25rem`（40–52px） | 1.1–1.2；仅强调帮助判断任务的真实数值，单位与总量保持邻近 |

- **建议**中文正文和标题不套用英文大标题的负字距。代码、路径和标识符按需使用等宽字体；变化中的计数和对齐数字列优先使用等宽数字特性，例如 `font-variant-numeric: tabular-nums`，不必更换整段文字字体。
- 紧凑模式优先减少行内留白、调整列和展开策略，而不是整体缩小字号。长文本与缩放时允许换行和增高，不用固定的行容器高度裁掉内容。
- 原生应用使用框架的逻辑单位和系统文字缩放；游戏根据实际显示尺寸、观看距离和 UI 缩放确定字号，不能直接照搬网页像素值。

### 4.3 布局、形状与图标

- **必须**统一同类控件的尺寸、间距、圆角和图标规格，并映射到现有主题变量或资源。不要另建一套与组件库冲突的数值。
- **建议**从 4、8、12、16、20、24、32 的间距节奏开始，赋予“标签间距、组内间距、区域间距、页面边距”等语义，而不是给每个页面另定一套值。数值按所用平台的逻辑单位解释。
- **必须**让相关内容靠近、不同分组有清晰间隔。标题与说明的距离应小于它们到下一组的距离；同级区域保持稳定的起始线和对齐关系。

无既有规则的 Web 信息工具可从以下留白起点选择，按内容量和视口调整：

| 关系 | 建议间距（CSS px） | 用途 |
|---|---|---|
| 图标与标签、标签与输入 | 8 | 让名称、单位和操作组成一个可读单元 |
| 标题与说明 | 8–12 | 保持标题组紧密，避免说明像另一个区域 |
| 同组字段／内容块 | 16 | 形成稳定阅读节奏 |
| 独立区域之间 | 24–32 | 用留白区分任务，而不是叠加卡片边框 |
| 详情面板内边距 | 20–24 | 主操作、错误和内容具有一致边线 |
| 页面内容边距 | 常规 24–32；窄屏 16–20 | 保留可读宽度，不机械等比缩放整个界面 |
| 列表行上下内边距 | 舒适 16–20；紧凑 10–12 | 字号不随密度档位整体缩小；命中区域仍满足适用要求 |

- 相邻间隔由一个布局层负责，避免父级 `gap` 和子级外边距无意叠加。行高、内容高度和命中区域分别设计，不用固定高度限制多行文字。
- 空间不足时，先收敛外边距和低频信息，再按内容需要折行或堆叠；主操作、状态与错误始终可达。留白服务于分组，不以大面积空白挤走任务内容。
- **建议**用表面、细分隔线和对齐表达普通层级；阴影主要表达浮层或确有意义的抬升。圆角按组件角色统一，不要求所有东西都变成圆角卡片。
- 图标按钮**必须**具有可访问名称；陌生或高风险操作优先显示文字。图标风格在同一功能区域保持一致。
- 素材须有明确用途、来源和可用授权；缺少素材时调整设计，不能把占位图作为完成品。

### 4.4 动效

- 动效用于解释状态和空间变化。**必须**避免无意义循环和无故延迟输入响应；工具控件不能在用户操作时因装饰动画移动位置。游戏中的移动目标按玩法设计，不套用工具控件规则。
- **必须**提供适用的减少动效方式：Web 优先响应系统偏好；原生和游戏使用平台能力或设置。保留关键反馈的静态或低动效表达。
- **建议**工具界面优先复用组件库时长；新增微交互可从 120–200ms 试起。游戏和叙事动画另定时序，不套用这个范围。

## 5. 定义行为，不只定义外观

### 5.1 控件与页面状态

存在对应交互时，**必须**定义默认、悬停（适用指针设备）、键盘焦点、按下、选中、禁用、忙碌、成功和错误状态。只读与禁用不同：只读内容通常仍需可读取、选择或复制。

- 悬停不是唯一入口；项目支持的触控或键盘路径也能完成相同任务。
- 禁用原因在用户需要知道时可获得，不把解释藏在无法触发的禁用按钮上。
- “没有数据”“没有筛选结果”“没有权限”“加载失败”分别给出正确原因和适用操作。
- 全局错误放在页面层，字段错误靠近字段，局部任务错误留在任务附近。不能只用短暂通知承载需要用户处理的问题。
- 悬停、键盘焦点和持续选中是不同状态；指针移开后，用户仍能识别选中对象。装饰性反馈不改变控件尺寸或挤动相邻内容。
- 列表异步刷新保留正在使用的焦点、输入和有效选择；不因每次进度更新而重建交互上下文。焦点所在操作消失或被禁用时，按组件及项目规则安置焦点，优先同一任务内的下一可用操作，而非任意跳回页面顶部。

### 5.2 表单与高风险操作

- 输入具有持久标签；占位符只作示例。单位、格式、必填条件和范围在相关字段旁说明。
- 校验失败保留有效输入，指出具体字段及修正方法；提交后让用户能定位错误。中文输入法组词时不得误触发提交或全局快捷键。
- 按钮使用动作名称，例如“保存设置”“导出 CSV”“删除 3 项”，避免在不同任务中都写“确定”。
- 修改已保存数据时，明确保存方式及未保存状态。离开提示用于真实的数据丢失风险，不对每次页面跳转弹确认框。
- 不可逆或高影响操作说明对象、范围和后果，使用确认或其他有效保护。可可靠撤销的低风险操作优先提供撤销，不叠加多次确认。

### 5.3 长任务、批量任务与恢复

- 提交后及时给出已接收、排队或执行中的真实状态；防止同一次用户意图被重复提交。
- 有可靠总量才显示百分比或“已完成／总量”；否则显示当前阶段和活动状态，不编造进度、剩余时间或成功。同一对象在列表、详情、进度条和结果中的数量与状态保持一致，放大数字不改变数据含义。
- “取消请求中”与“已取消”分开；关闭窗口或弹层与停止任务分开。未实现暂停、续跑或取消的能力不能放出可用按钮。
- 批量任务显示完成、失败、跳过和未处理的范围；重试只作用于实际需要重试的对象，不能悄悄重复成功项。
- 失败说明已知原因、影响和可执行的恢复动作。保留可用结果；无法恢复或无法后台继续时，在离开前说明实际影响。
- 输出文件或成果给出可用入口。日志细节可展开，但不暴露密钥、会话凭据等敏感数据。

### 5.4 对话框、展开区与导航

- 模态对话框打开后将焦点放到合适位置；背景不可操作；关闭后返回触发控件或合理的后续位置。必须有可发现的退出方式。
- Web 模态对话框的 Tab 焦点循环、Escape 关闭及名称关联按 [WAI-ARIA 对话框模式](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)实现。关闭不等于取消后台任务；未保存或不可中断操作另有清楚的行为定义。
- 弹层以实际可见区域定位；长内容、窄窗口、软键盘或嵌入容器中，标题、关闭入口、错误与提交操作仍可访问。需要滚动时使用明确的内容滚动区，不能把主按钮固定在不可见位置。
- 非模态面板不套用模态焦点锁定。页面切换、筛选、排序和选择不能无故重置用户正在使用的上下文。
- 筛选后优先保留仍在结果内的选中项；若它不再可见，按项目规则清空详情、选择可见项，或明确提示“所选对象在筛选外”。不能让列表和详情暗中对应不同对象；无结果状态不得留下无说明的旧对象操作。
- 展开控件显示名称和展开状态，支持目标输入方式；Web 优先原生展开控件或成熟组件。展开／收起不重置任务或有效输入，不反复自动收起用户正在查看的内容。
- 自定义菜单、树、标签页等优先复用成熟控件的键盘模型，不把所有元素都变成无语义的可点击容器。

## 6. 可读、可操作的验收底线

以下条目是本规范选取的常见检查项。Web 项目以 WCAG 2.2 A/AA 为无障碍目标；对外声明完整符合时，须核验所有适用成功准则，而非只勾选本文清单。原生应用和游戏采用对应平台的可访问性能力，不将 CSS 单位直接换算成设备像素。[WCAG 2.2](https://www.w3.org/TR/WCAG22/)

### 对比度

- Web 普通文字与背景至少 **4.5∶1**；符合 WCAG 大文本定义的文字至少 **3∶1**。大文本指至少 18pt 常规或 14pt 粗体，约为 24 或 18.67 CSS px。辅助说明不因“次要”而豁免。[文字对比度](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)
- 识别控件、状态和有意义图形所必需的视觉信息，与相邻颜色至少 **3∶1**。纯装饰和标准规定的例外按其适用条件处理；不要要求每一条装饰线都达到该值。[非文字对比度](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)
- 渐变、透明背景、图片和游戏场景中的文字检查实际组合；必要时增加稳定底板、描边或阴影。不能只检查色板样本。

### 输入、焦点与语义

- 支持键盘的业务界面可仅用键盘完成主要任务，顺序符合内容关系；无焦点陷阱。控件的名称、角色、值和状态通过平台可访问性接口提供。
- 焦点清晰可见；浮层和固定栏不能把当前焦点控件完全遮住，优先使其完整可见。[焦点不被遮挡](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)
- 非文本内容有合适的替代说明；错误和重要状态变化能被辅助技术感知。动态日志不能持续抢焦点或无节制播报。
- Web 指针目标遵循 WCAG 2.2 AA 的 **24×24 CSS px** 最小目标及其间距等例外。项目**建议**将主要触控目标做到至少 **44×44 CSS px**。扩大命中区不能造成相邻控件重叠。[目标尺寸](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

### 缩放与重排

- Web 普通文字支持放大至 **200%**，在支持的放大过程内不丢失内容或功能；不要用固定高度裁掉文字。[文字缩放](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html)
- 普通纵向阅读内容在 **320 CSS px** 等效宽度下重排，避免整页双向滚动。横向阅读内容对应 256 CSS px 等效高度。数据表、地图、游戏画布等必须二维布局的部分可局部滚动；例外不自动扩展到整个页面。[重排要求](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)

## 7. 只叠加实际需要的平台规则

### Web 应用与网站

- 优先语义化 HTML 和组件库已有行为；断点由内容开始拥挤的位置决定，不凭品牌模板照抄。
- 主操作、错误、弹层和固定栏在窄视口、缩放、软键盘出现时仍可访问。兼容范围写入项目规范，不默认覆盖所有浏览器。
- 展示网站可以使用大图、强字号对比和更充分的动效；实际表单、导航和可读性仍遵循基线。

### 桌面原生应用与桌面 Web 容器

- 保留平台的窗口、菜单、文件选择和常用快捷键习惯；优先标准控件及其可访问性实现。
- 明确最小窗口尺寸及显示缩放支持；在目标环境检查 DPI、系统文字放大、多屏切换或高对比模式中与本次改动相关的行为。
- 尺寸使用框架逻辑单位；桌面 Web 容器同时检查网页内容和宿主窗口，不以其中一个通过代替另一个。[Windows 包容性设计](https://learn.microsoft.com/en-us/windows/apps/design/accessibility/designing-inclusive-software)

### 浏览器扩展、嵌入面板与浮层

- 以实际容器大小设计；设置页和弹出窗口可使用不同信息密度，不把完整后台等比缩小。
- 样式和事件作用域不能污染宿主，也不能被宿主常见样式轻易破坏；覆盖内容有明确关闭和恢复入口。
- 不抢占输入、滚动和宿主快捷键。复制、选择、撤销以及原页面可读性按功能要求保留。
- 弹出窗口关闭后任务是否继续，必须与真实运行机制一致；权限请求由相关操作触发并说明用途。

### 游戏与实时画布

- HUD、菜单、背包、对话和工具面板分开设计；重要信息按战斗、探索、暂停等实际状态安排，避免遮挡目标、字幕或操作区。
- 定义参考画布、宽高比、安全区、UI 缩放及目标观看距离。用真实场景检查明暗变化、动效背景和小屏文字，而不只看静态菜单。[XAG 101：游戏文字显示](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/101)
- 为已支持的鼠标、触控、键盘或手柄定义焦点、返回、确认和提示图标；菜单不能在输入切换后丢失可操作路径。
- 需要即时反馈时保持反馈及时；减少动效不能使关键状态消失。声音、颜色或振动不作为重要信息的唯一通道。
- 游戏主循环保留其交互特征；设置、存档、错误和购买等工具性流程仍遵循适用的通用行为规范。

## 8. awesome-design-md 只作可选视觉参考

参考库：[VoltAgent/awesome-design-md](https://github.com/VoltAgent/awesome-design-md)。不默认下载全库，也不要求每次 UI 工作联网查阅。

采用某一份参考时：

1. **先确认对象。** 它分析的是官网、后台、客户端还是其他表面？官网的截图卡片不代表实际产品组件规范。
2. **选择一个主要方向。** 提取有用的颜色角色、排版节奏、形状与构图；其他参考仅解决明确缺口，不拼接互相矛盾的整套规则。
3. **记录取舍。** 在项目 `DESIGN.md` 写入文件 URL、提交或版本、查阅日期、采用项、排除项。推断规则标成推断，未验证部分不能写成已确认。
4. **转换为自己的规则。** 补齐真实任务需要的状态、中文字体、缩放和平台交互，解决原文矛盾；不保留不适用的“必须使用该品牌字体／禁止浅色”等限制。
5. **落实并验证。** 映射到当前组件与主题，再检查实际页面。参考库更新不自动同步到项目；变更只在有需求时评估。

## 9. 文档、组件与代码保持同一套含义

- `DESIGN.md` 负责记录用户任务、设计决策和组件使用方式；主题文件与组件实现负责提供实际数值和行为。明确各自的权威来源，避免长期维护两份不同的 token 表。
- 沿用已有变量、主题资源和组件入口。只有现有能力无法满足明确需求时才扩展，不为了套模板重写所有控件。
- 项目状态变化、支持平台变化或组件替换时，同步更新直接相关的规则、示例和验收点。
- 标出真实未解决问题、影响范围及处理人。一般设计细节由实现者按规范决定，不把每个颜色或间距都变成审批事项。

## 10. 用实际结果验收

每次只检查本次变化及其直接影响，复用同一候选版本下仍有效的证据。推荐记录：页面／场景、版本、环境、步骤、预期、实际结果、证据位置。

- [ ] **任务完整：** 关键入口到结果实际走通；最相关的失败路径可恢复，数据含义和原有入口保持正确。
- [ ] **状态真实：** 用适合的真实数据或明确标记的测试数据检查空、忙碌、错误及必要的部分成功状态；操作能力与后台一致。
- [ ] **实际渲染：** 在主要使用环境和最容易失败的布局条件下查看界面；中文、长文本、单位、路径、数值和内容覆盖正确。
- [ ] **层级与留白：** 同类文字角色一致，标题组与区域间距有区分；舒适／紧凑模式不牺牲可读性，关键操作先于低频技术细节。未新增与任务无关的装饰或空白。
- [ ] **适用尺寸：** Web 检查窄视口及文字缩放；桌面检查目标缩放和最小窗口；扩展检查真实容器；游戏检查真实场景、安全区及输入方式。仅做适用项。
- [ ] **可操作性：** 键盘或目标替代输入、焦点、对话框、展开区、标签和错误提示可用；异步更新与筛选后的对象和焦点正确。涉及语义变更时检查可访问性树及必要的辅助技术路径。
- [ ] **视觉与资源：** 所支持主题、实际颜色组合、命中区域和素材均符合已选规则；不存在明显遮挡、溢出或未替换的占位内容。
- [ ] **实现一致：** 相关自动化检查通过，设计规则与实际组件一致。测试通过不能替代实际交互和视觉验收。

必要检查未完成时，写明影响、下一责任人和恢复条件。影响本次关键路径的问题须解决后交付；范围外的既有问题单独记录，不扩大为无关项目的整改任务。
